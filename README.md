# 货运数仓来源核对

货运数仓收到两份没标版本的导出 CSV(运单表导出、签收表导出),本工具用一份
JSON 证据包(两表起点快照 + 起止提交号 + 逐事务行变更前后值)重放提交历史,
判断两份 CSV 是否可能来自同一次提交。

此外提供**补档**入口:事务日志少了一笔时,用缺一笔的证据包 + 末次提交后的
两表全量快照,按首尾快照推算缺号前后的两表状态,补齐净变更并生成可完整重放到
末快照的证据包。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

页面顶部有两个页签:

- **来源核查**:上传运单导出 CSV、签收导出 CSV、证据包 JSON 三份文件。
- **补档**:上传缺一笔的证据包 JSON + 末次提交后的两表全量快照 JSON。

各页底部可直接下载对应样例;补档样例可一键补出提交 102 的「快照推算」净变更,
再回到核查页复查。

本地自测(不需要 Docker):

```bash
pip install -r requirements.txt   # HTTP 接口测试需要 fastapi/httpx
python3 -m tests.selftest         # 主核查 + 补档两套自测
```

只跑补档自测:

```bash
python3 -m tests.recovery_selftest
```

## 输入格式

### 运单导出 CSV

只含已签收运单,列:`单号,状态,件数`(UTF-8,键 `单号` 不可重复)。

### 签收导出 CSV

只含已签收运单的签收明细,列:`签收号,单号,实收件数`(键 `签收号` 不可重复)。

### 证据包 JSON

```json
{
  "start_commit": 100,
  "end_commit": 110,
  "snapshots": {
    "waybills": [{"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"}],
    "receipts": [{"签收号": "RC0001", "单号": "WB0001", "实收件数": 3, "签收人": "张三"}]
  },
  "transactions": [
    {"commit": 101, "changes": [
      {"table": "waybills", "op": "update", "key": "WB0001",
       "before": {"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"},
       "after":  {"单号": "WB0001", "状态": "已签收", "件数": 4, "目的地": "上海"}}
    ]}
  ]
}
```

- 表名支持 `waybills`/`运单表`、`receipts`/`签收表`;`op` 为 `insert`/`update`/`delete`
  (insert 的 `before` 为 null,delete 的 `after` 为 null)。
- 快照行可含任意额外列,导出比对只取规定字段;但变更 `before` 必须与重放出的
  整行完全一致(含额外列),否则视为前值对不上。
- 数值比较按字符串归一化:JSON 数字 `3` 与 CSV 文本 `"3"` 视为相等。

## 判定规则

- 导出视图:运单导出 = 状态为「已签收」的运单,取(单号, 状态, 件数);
  签收导出 = 单号属于已签收运单的签收行,取(签收号, 单号, 实收件数)。
- 只在**起点**(起始提交号)和**每笔事务整体应用之后**与 CSV 比对;
  键集合与对应值完全一致(按编号和值)记为一个吻合提交。
- 输出:各文件完全吻合的提交区间、两者的交集;交集为空时提示
  「所查范围内没有共同来源」。
- 下列情况提示「证据不足」并停止核查:
  - 日志缺号:提交号不连续、尾部缺失或超出终止提交号;
  - 变更前值与重放状态对不上(含 insert 前键已存在、update/delete 前键不存在);
  - 起点快照键重复或缺键列。
- 变更条数上限 50000 条,超出直接拒绝。

## 补档规则

补档用于「事务日志少了一笔」的核查场景,输入两份文件:

1. **缺一笔的证据包**:与核查用证据包同格式,但 `transactions` 的提交号在
   `start_commit+1 .. end_commit` 中恰好缺一个,其余日志齐全。
2. **末次提交后的两表全量快照**:`{"waybills": [...全表...], "receipts": [...全表...]}`,
   也兼容外面再包一层 `snapshots` 或中文表名。这是末次提交后的整表状态,不是导出视图。

推算步骤:

- **前推**:从起点快照出发顺序应用缺号之前的日志,逐条核对每条变更的 `before`
  (同一笔里同一行改过多次也逐条核对,任一前值对不上即失败),得到缺号**前**的两表状态。
- **回推**:从末快照出发逆序反做缺号之后的日志,逐条核对每条变更的 `after`,得到缺号**后**的两表状态。
- **净变更**:比较缺号前后两表,把运单表与签收表的净变更(每行至多一条
  insert/update/delete)合并成**同一笔**事务,插入原日志缺号位置,提交号即缺号,
  并标 `"source": "快照推算"`。原事务原样保留、顺序不变。
- **完整重放**:用补齐后的包从起点快照重放一遍,必须恰好落到末快照;否则说明原因、不给下载。

下列情况说明原因且**不提供下载**:

| 情况 | HTTP | 说明 |
| --- | --- | --- |
| 缺号数不为一(0 个或多于 1 个) | 422 | 「缺号数不为一」 |
| 日志提交号重复 | 422 | 「日志重复」 |
| 日志提交号乱序 | 422 | 「日志乱序」 |
| 前推/回推时行值对不上 | 422 | 指明提交号与变更序号 |
| 补齐后变更总数超过原上限 50000 | 422 | 给出原有/新增/合计条数 |
| 证据包或末快照结构非法 | 400 | 「输入有误」 |

补齐后的包可直接作为「来源核查」的证据包上传复查。若**推算出的提交**落在两份
CSV 的共同来源里,核查页会把该提交号标黄并注明「快照推算」,表示它并非原始日志。

## 性能设计

不为每次提交复制整表。重放时维护:

- 两张表的当前行(按主键的字典);
- 已签收单号集合、单号 → 签收号索引;
- 两个「当前导出视图 vs 目标 CSV」的差异计数器。

每条变更只触碰受影响的键:运单变更 O(1) 更新运单侧计数,签收状态翻转时只扫描
该单号名下的签收行;签收变更 O(1)。整体复杂度 O(快照行数 + 变更条数),
5 万条变更在本机自测约 1 秒内完成(见 `tests/selftest.py`)。

## 自测覆盖

`python3 -m tests.selftest`(主核查 + 补档两套):

核查:

1. 样例场景端到端区间/交集断言;
2. 每个提交后增量计数与全量重算一致(验证不复制整表的增量逻辑正确);
3. 交集为空 → 无共同来源;
4. 日志缺号(中间/尾部)、前值对不上、提交号超出终止号 → 证据不足;
5. 签收行改挂单号、运单状态翻转带多签收行的边界场景;
6. CSV 缺列/重复键校验;
7. 5 万条变更性能与正确性;
8. HTTP 接口(上传样例、缺号证据、坏 CSV、操作页、样例下载)。

补档(`tests/recovery_selftest.py`):

1. 缺中间一笔 → 定位缺号、推算净变更、原事务原样保留、补齐包可被核查;
2. 缺首笔/缺末笔;
3. 同一笔里两表净变更、同一行改多次合并为一条净变更、前推/回推逐条核对;
4. 缺号数不为一、日志重复、日志乱序、前值/后值对不上、末快照对不上、
   补齐后超过 50000 → 拒绝;
5. 补齐后恰好 50000 条 → 允许(边界);
6. 缺号前后状态相同 → 空推算事务仍可重放;
7. 证据包结构非法 → InputError;
8. 核查页透传「快照推算」标记(含在/不在交集两种情况);
9. 补档 HTTP 接口:成功可下载、失败不给下载且说明原因、非法 JSON;
10. 补档后把下载的包重新上传核查,仍通过且显示标记。

## 已知限制

- 「已签收」状态值固定为 `已签收`(app/core.py 中 `SIGNED_STATUS`)。
- CSV 只校验必需列,额外列不参与比对。
- 证据包整体读入内存解析,未做流式 JSON;5 万条变更规模下足够。
- 行键(单号/签收号)在变更中不可改:after 行的键必须与记录键一致。
- 补档只补**一笔**(一个缺号);缺零笔或多笔都会拒绝。
- 补档推算的是缺号处两表的**净变更**,不是原始逐条操作;若同一行在缺号那一笔里
  被改了多次,只能还原为该笔的整体前后值。
- 末快照必须是末次提交**之后**的整表全量行(含未签收运单等导出视图之外的行),
  否则回推核对会报行值对不上。
